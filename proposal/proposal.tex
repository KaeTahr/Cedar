Systems programming is an area of software development that relies on precise
control over hardware resources and system-level abstractions. For this reason,
systems programming languages are often low-level, allowing developers to write
efficient code that can directly manipulate memory and hardware. However, this
low-level access comes at the cost of increased complexity and potential
for errors. Specifically, C and C++ are two of the most widely used systems
programming languages, but they are also known to be error-prone and difficult
to use. In order to address these issues, many researchers have proposed
new programming languages and tools that aim to improve the safety and
efficiency of systems programming. One way to reduce the errors in systems is
to use a type system that is proven to be sound, and guarantees that the
programmer's intent is preserved. In this project we will propose a Cider, a new
domain specific language (DSL) for type definition that is sound and
guarantees that the programmer's intent is preserved. This project originates
from previous work done in Dargent \cite{dargent2023cider}, a research
programming language that is meant to be used in low-level systems, but
allows higher-level abstractions.
Previous theoretical work and some implementations have been done to create
a a language with this purpose, and in this project we aim to build upon
this work, and develop a compiler for Cider. Previous works implements a
transpiler that allows programmers to define most types defined in C, however lacks
a preprocessor, custom sizer, and recursive types, which limit its usefulness.
This transpiler so far allows programmers to define types, and then compile
the to C.
We aim refine the language to allow for these features, proving correctness
and soundness of all features along the way. 
In this manner, this project aims to answer the following research
question: 
How can we design a sound type system for a systems programming language that
is both expressive and efficient?

In systems programming, the precise control over data layout is essential
for software that operates at high performance, and is secure at 
lower levels. Languages like C offer minimal abstraction over
memory,which allows programmers to write efficient code, but also
places a burden on them, to manually define binary layouts through
bit-fields, unions and other constructs depending on the platform.
This approach, although appreciated for its flexibility, is 
notorious for being error-prone, particularly in performance-critical
contexts, such as hardware registers, where memory alignment matters.

Traditionally, developers have resorted to marshalling code, or unsafe
macros to translate between structure data and low-level binary formats.
These techniques are difficult to maintain, inefficient, and almost
impossible to verify formally, often leading to subtle bugs and
security vulnerabilities. This stems from lack of separation, or
abstraction, between what a data structure represents and how it is
laid out in memory, which hinders reasoning about correctness.

Recent projects and research has explored approaches to describing
data layouts, One notable example is Dargent, a data Layout
language integrated into the Cogent language, which enables programmers
to declaratively specify memory layouts for algebraic data types. 
\section{Background}
\subsection {Data Layout Challenges in C}
Systems programming relies on the programmer having low-level control over
hardware resources, and for this reason, C is often used as the language of
choice. However, this low-level access comes at the cost of increased complexity
and potential for errors. Specifically, C is known to be error-prone and
difficult to use, and this is especially true when it comes to data layout.
Data layout is the process of determining how data is stored in memory, and
manual control of this is critical in systems programming. However, this
also comes at the cost of it being inherently unsafe, as the programmer must
ensure that the data is laid out correctly, and that the memory is accessed in
a safe manner. Tools like Valgrind and AddressSanitizer have been developed to
assist programmers in this task, but they are not foolproof, and rely on 
error detection at runtime. While this process of top-down programming is
useful, it is not always the most efficient way to write code, and in the end
it does not guarantee correctness. In order to address these issues, new
programming languages and tools have been proposed that aim to improve the
safety and efficiency of systems programming. The most well known of these is
Rust, which is a systems programming language that is designed to be safe and
efficient. However when it comes to delicate data layout, Rust is not
always safer, as it may be necessary to use unsafe code in order to achieve
the desired performance. This is where Cider comes in, as it is a DSL
for type definition that is designed to be used in low-level systems programming
allowing programmers to define types in a way that is both safe and efficient.
\subsection{Dargent and Cogent}
Dargent is a data layout description language and refinement framework integrated
into the Cogent language. Cogent is a purely functional programming language
designed to to generate efficient and verifiable C code for low-level components,
such as file systems and device drivers. It is supported by a certyfying
compiler that generates C code, alongside proofs in Isabelle/HOL.
In this context, Dargent enhances Cogent, by allowing developers to
describe algebraic data types in terms of their memory layout. It aims to
prevent the need for marshalling and un-marshalling data, which is a common
common a common performance bottleneck in low-level programming. Instead, 
Dargent generates C code that directly manipulates the memory along with
setter and getter functions for safe access, all while generating proofs of
correctness.
Dargent's design of allowing layouts to be written independently of types, which
allows the layouts to be evolved independently of the program's logic, all while
ensuring well-formed layouts, ensuring non-overlapping fields, valid offsets,
and bit-aligned representations.
Dargent is an extension of Cogent, and as such it integrates seamlessly into it.
Its compiler generates the getters and setters for each layout, which
manipulate the memory directly. Proof of correctness is also generated during
the compilation process, providing a combination of high-level control
and abstraction with formal guarantees.
\subsection{Cedar}
Cedar builds upon the work done in Dargent, and aims to essnetially be a 
"Dargent for C". It aims to be directly compatible with C, and be more broadly
applicable. It is a layout description language that integrates directly into C,
implemented as a transpiler in Haskell. 
Currently, Cedar allows programmers to memory layout constructs, which are
associated to C structs via syntactic annotations. The transpiler
includes modules for lexical and semantic analysis, reduces the Cedar
data types and layout specifications.
Cedar currently lacks a formal verification backend, however it preserves
the advantages of Dargent: declarative layout specifications, syntactic
clarity, rigorousness. Importantly, as it is designed to work with the
C language, and not a heavily restricted subset, it increases its
practical utility for systems programmers.
The project lays the groundwork for integration with verification systems,
such as CompCert.

\section{Research Plan}
This project aims to explore the design of a data description language for C.
In this context we propose the question: \b{How can we design a data description language that is practical
for systems programming, while being sound and expressive for C?}.

\subsection {Literature Review}
This first phase involves a comprehensive literature review to understand the
design space and trade-offs in existing verified systems languages and tools.
This includes:
\begin{itemize}
    \item A review of the tools closest to cider, Dargent and Cogent, to
    understand their desing, verification architecture, layout-type matching
    and formal semantics. 
    \item Reviewing CompCert, as it is the compiler that is being targeted by
    Cider, and to understand how C semantics are formalised. 
    \item A survey of the current state of the art in type systems for systems programming
\end{itemize}

    \item The limitations of the current semantics
    \item The limitations of the current tooling
\end{itemize}
